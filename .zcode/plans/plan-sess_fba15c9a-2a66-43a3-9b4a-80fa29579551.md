# ifafu-kyzz 稳定性增强：崩溃处理 + 错误反馈 robust 化

## 设计原则
- **零新第三方依赖**（不引入 Bugly/ACRA/Timber，全部自建）
- **聚焦核心基础设施**：不动现有 9 个 ViewModel 的 State 结构，不迁移 showError（降低回归风险）
- **复用现有机制**：反馈通道复用 `GitHubIssuesApi` 的 token 和模式，发到专门的 Issue

## 第二部分：崩溃处理重做（核心）

### 2.1 新增 `core/crash/CrashReporter.kt`（崩溃落盘 + 防循环）
职责：
- 把崩溃 trace/message/time/设备信息（机型/Android版本/应用版本/进程名）**写入文件** `files/crash/crash_<timestamp>.txt`（保留最近 10 个，旧的自动清理）
- 同时保留原 `ifafu_crash` SharedPreferences 的崩溃计数和防循环逻辑（10s 内 >=3 次停 `MockLocationService`）
- 提供读取接口：`getPendingCrashReport(): CrashInfo?`、`clearPendingCrash()`、`getAllCrashFiles()`
- 写文件操作全程 try-catch，避免 handler 自身崩溃

### 2.2 重写 `MainApplication.CrashHandler`
- 改为调用 `CrashReporter`
- 记录"上次崩溃未反馈"标记到 `ifafu_crash`（`pending_crash_feedback = true`）
- 保留原有的重启到 MainActivity + `crash_recovery` extra + 防崩溃循环逻辑
- 在 `defaultHandler.uncaughtException` 前完成所有持久化

### 2.3 `MainActivity` 消费崩溃恢复（让 `crash_recovery` extra 真正生效）
在 `onCreate` 检查 `intent.getBooleanExtra("crash_recovery", false)`：
- 若为 true 且 `CrashReporter.getPendingCrashReport() != null`，弹出恢复对话框：
  - 标题"应用已恢复"+ 显示崩溃摘要
  - 按钮"反馈问题"→ 打开崩溃反馈页（见 2.4）
  - 按钮"忽略"→ 清除 pending 标记，正常继续
- 防止反复弹窗：只在有 pending crash 时弹一次

### 2.4 新增崩溃反馈页 `ui/feedback/CrashFeedbackActivity.kt` + layout
- 展示崩溃详情（trace、时间、设备信息）可滚动
- 可编辑的"补充说明"输入框（用户可描述操作场景）
- "提交反馈"按钮 → 调用 `CrashReportApi`（见 2.5）上报到 GitHub Issue，成功后清除 pending
- "复制到剪贴板"按钮（作为离线反馈兜底）
- 风格沿用应用的 Claude 主题配色（claude_terracotta 等）

### 2.5 新增 `data/api/CrashReportApi.kt`（崩溃上报通道，复用 GitHubIssuesApi 模式）
- 复用 `BuildConfig.GITHUB_TOKEN_ENC` + KeyGuard
- `suspend fun reportCrash(crashInfo: CrashInfo, userDescription: String): Boolean`
- 以 comment 形式发到 ifafu-kyzz-comment 仓库的**专门 Issue（#3）**，body 为结构化 JSON：`{type:"crash", trace, message, time, device, appVersion, description}`
- 失败静默返回 false，不影响用户

## 第三部分：全局错误事件总线

### 3.1 新增 `ui/event/GlobalEvent.kt`（单次事件总线）
```
object GlobalEventBus {
    // 基于 MutableLiveData<Event<T>> 的 SingleLiveEvent 模式
    // 全局事件：SessionExpired, Toast(message), CrashFeedbackPending
    val events: LiveData<Event<GlobalEvent>>
    fun emit(event: GlobalEvent)
}
sealed class GlobalEvent {
    object SessionExpired : GlobalEvent()       // 会话过期，统一跳登录
    data class Toast(val message: String) : GlobalEvent()
}
```
- 用 `Event<T>` 包装防止消费后重复触发（SingleLiveEvent 思路）
- 在 `MainApplication.onCreate` 初始化单例

### 3.2 `BaseActivity` 订阅全局事件
在 `onCreate`（super 之后）订阅 `GlobalEventBus.events`：
- `SessionExpired` → 跳 `LoginActivity` 并 finish 当前（统一的会话过期处理，取代各 ViewModel 各自判断 isSessionExpired 后弹错误）
- `Toast` → 全局 Toast 兜底
- 订阅用 `lifecycleScope`，保证生命周期安全

### 3.3 `AlertException` 触发全局事件
在 ViewModel 基类（见第四部分）捕获 `AlertException` 且 `isSessionExpired` 时，调用 `GlobalEventBus.emit(GlobalEvent.SessionExpired)`，而不是只设 `UiState.Error`。现有各 ViewModel 的 catch 块保留兼容，但新机制统一收口。

## 第四部分：协程异常统一处理

### 4.1 改造 `ui/base/ReloginViewModel.kt`（从空壳变为基础能力）
```kotlin
abstract class ReloginViewModel : ViewModel() {
    // 提供统一的 CoroutineExceptionHandler
    protected val coroutineExceptionHandler = CoroutineExceptionHandler { _, e ->
        when (e) {
            is CancellationException -> throw e   // 必须重抛
            is AlertException -> {
                if (e.isSessionExpired) GlobalEventBus.emit(GlobalEvent.SessionExpired)
                onUnhandledError(e.message ?: "操作失败")
            }
            else -> onUnhandledError("网络异常，请稍后重试")
        }
        Logger.e(TAG, "ViewModel coroutine error", e)
    }

    // 子类可选覆盖：未处理错误的兜底（默认空实现，不强制改）
    protected open fun onUnhandledError(message: String) {}
    companion object { private const val TAG = "ReloginViewModel" }
}
```
- **向后兼容**：现有 21 个 ViewModel 不强制改动。它们仍用各自的 try/catch，`coroutineExceptionHandler` 只是可选的兜底（子类可在 `viewModelScope.launch(handler)` 时传入）
- 提供 `launchSafe { }` 扩展函数：自动包裹 try/catch + handler，新代码推荐使用

### 4.2 新增 `launchSafe` 助手
```kotlin
fun ViewModel.launchSafe(
    onError: (Exception) -> Unit = {},
    block: suspend CoroutineScope.() -> Unit
): Job
```
封装统一的 `CancellationException` 重抛 + `AlertException` 处理 + 兜底 catch + 异常日志。新 ViewModel / 重构时使用，不强制改老的。

## 第五部分：轻量 ANR 监测 + StrictMode

### 5.1 新增 `core/anr/AnrWatchdog.kt`（主线程阻塞监测）
- 后台线程每 2s 向主线程 post 一个 tick 任务，5s 内没执行 → 判定主线程阻塞
- 记录为"疑似 ANR"写入崩溃日志目录（`crash/anr_<timestamp>.txt`），可被反馈机制一并提交
- 阈值保守（5s，低于系统 ANR 的 5s），避免误报
- 在 `MainApplication.onCreate` 启动，仅做记录不杀进程

### 5.2 `MainApplication` debug 开启 StrictMode
- `if (BuildConfig.DEBUG)` 开启 `StrictMode`（detect 主线程 disk/network 违规，penaltyLog 到 logcat）
- release 不开启，避免误报干扰

## 验证方式
- 编译通过（`./gradlew assembleDebug`）
- 手动验证：可在 MainActivity onCreate 临时加 `throw RuntimeException("test")` 触发崩溃，确认：落盘日志生成 → 重启弹恢复对话框 → 反馈页能提交/复制 → pending 标记清除
- 验证防崩溃循环：连续触发 3 次确认 MockLocationService 停止、计数重置
- 验证 ANR：临时在主线程 sleep(6s)，确认 anr 日志生成
- 移除所有测试代码

**预期收益**：崩溃可追溯（落盘）、可反馈（一键到开发者）、会话过期不再各自为政、协程崩溃有统一兜底、主线程卡顿可感知——整体稳定性显著提升，且零新依赖、低回归风险。
